# SmartCommute — documentation

| Document | What it is | Audience |
|---|---|---|
| [UCN/](UCN/README.md) | **Use case narratives** `UCN_SC_E001` – `E028`: the implemented behaviour of every feature, with flows, exceptions, known gaps and code references. `UCN_Combined.md` is the same set in one file, generated by `UCN/build_combined.py`. | Everyone |
| [Use_Case_Diagram.md](Use_Case_Diagram.md) | UML use-case diagram of the whole system, an actor / use-case catalogue, and the **split diagrams** (PNG) for pasting into Google Docs or Word. Sources and generators in [`diagrams/`](diagrams/). | Analysts, report writers |
| [Functional_Requirements.md](Functional_Requirements.md) | What the system shall do: **one requirement per use case** (`FR-E001` = `UCN_SC_E001`, 28 in all), each with its acceptance criteria, plus the known gaps (`GAP-…`, not requirements). | Analysts, testers |
| [Non_Functional_Requirements.md](Non_Functional_Requirements.md) | Security, privacy, reliability, performance, usability… (`NFR-…`, 91 in all), **each tied to evidence**: the tests that verify it and their result (✅ Pass / ❌ Fail / ⚪ Not tested). Known gaps are executable tests that fail on purpose (`--group nfr-gap`). Also lists the defects the tests found. | Analysts, reviewers, testers |
| [Entity_Relationship_Diagram.md](Entity_Relationship_Diagram.md) | Summary and full ERD (35 tables, 49 relationships, read from the live schema), table groups, and schema findings the UCNs do not state. | Developers, report writers |
| [AUTOMATED_FEATURES.md](AUTOMATED_FEATURES.md) | Everything the system does by itself — scheduled jobs (auto clock-out, inactivity check, payment reconciliation, maintenance alerts, replacement drivers, reports, flags, clean-up), emails, the violation offense picker, QR-scan attribution and the phone scan of vehicle papers — with triggers, config and code locations. | Everyone |
| [AUDIT_TRAIL.md](AUDIT_TRAIL.md) | How the audit trail (`activity_log`) works: what is recorded, the event catalogue, how to add to it, the admin Activity Log page, and how to roll it out to another environment. | Developers |
| [MANUAL_TEST_CHECKLIST.md](MANUAL_TEST_CHECKLIST.md) | Click-through checks by role and by automatic job, with seeded test accounts, and what each test round found. | Testers |
| [UCN_Test_Checklist.txt](UCN_Test_Checklist.txt) and [UCN_Test_Checklist/](UCN_Test_Checklist/) | The same use-case checks as printable text, whole and in five parts. | Testers |
| [UI_DESIGN_SYSTEM.md](UI_DESIGN_SYSTEM.md) | Colours, badges and components used by the views. | Developers |
| [PAYMONGO_SETUP.md](PAYMONGO_SETUP.md) | Enabling GCash / Maya checkout with PayMongo sandbox keys, and how reconciliation backs up the webhook. | Developers |

## Regenerating the diagrams

| Diagram | Command | Needs |
|---|---|---|
| Full use-case diagram | `python3 docs/diagrams/build_use_case_diagram.py` | Python 3 |
| Split use-case diagrams (SVG + PNG) | `python3 docs/diagrams/build_use_case_parts.py` | Python 3, Chrome (for the PNGs) |
| Summary + full ERD (SVG + PNG) | `python3 docs/diagrams/build_erd.py` | Python 3, Graphviz |

Edit the data block at the top of each script (use cases, groups, schema), then re-run it. After a migration, update `SCHEMA` / `REL` in `build_erd.py`.

## Keeping them honest

- Behaviour change → update its UCN (then run `python3 docs/UCN/build_combined.py`), `AUTOMATED_FEATURES.md` if it runs on its own, then the matching `FR-` / `NFR-` rows.
- New migration → update the ERD data and `Entity_Relationship_Diagram.md`. `SCHEMA` / `REL` can be regenerated from the database's `information_schema`.
- New use case → add a UCN sheet, a row in `UCN/README.md` and `UCN_Combined.md`, then the use-case diagram data and `Use_Case_Diagram.md`.
- Automated suites: `/opt/lampp/bin/php vendor/bin/phpunit` (they run against the dev database inside transactions, so run `php artisan migrate` first). `tests/Feature/Nfr/` holds the tests behind each non-functional requirement; `NfrTraceabilityTest` fails if that document cites a test that does not exist or its counts drift, and if the functional requirements stop being one per use case.
