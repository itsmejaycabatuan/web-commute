 BEFORE YOU START (everyone)
----------------------------------------------------------------------------------------------

 1. Load the baseline data (it adds what is missing; on a database that already holds drivers with other codes
    it can stop with "Duplicate entry 'DRV-000002'" - see MANUAL_TEST_CHECKLIST.md, so use a fresh database then):

        /opt/lampp/bin/php artisan db:seed --class=DevSeeder

 2. Start the app and browse to http://127.0.0.1:8000

        /opt/lampp/bin/php artisan serve

    Use 127.0.0.1:8000, NOT XAMPP Apache (Apache breaks the compiled-view permissions).

 3. Password for every seeded account is:  admin123
 4. Login is throttled to 5 attempts per minute. If you get "Too many attempts" (429), wait a minute.
 5. Team members share ONE database. If two people test at once, wallet balances, shifts and
    suspensions will change under each other. Agree who is on the server, or give each person their
    own copy, and re-run the seeder whenever the data looks wrong.
 6. Use a separate browser profile (or private window) per role so sessions do not collide.

 HOW TO USE THIS CHECKLIST

   - Work through your part top to bottom. Tick a box by changing [ ] to [x].
   - If a step FAILS, change it to [F] and write what you saw on the "Notes" line (or on the line below).
   - If a step cannot be tested, change it to [-] and say why.
   - Every use case has three groups:  MAIN FLOW (happy path), ALTERNATE FLOWS (A1, A2...),
     and EXCEPTIONS (E1, E2... = what happens when something goes wrong).
   - The text after "->" is the EXPECTED result. Messages in quotes should match what the screen shows.
   - Finish each use case with the RESULT line: tick PASS only if every step above it is [x] or [-].
   - (*) marks a step that needs a fault to be forced (database down, mail server down, payment gateway
     down, lost network). Do not break the server just for this - mark it [-] unless a developer
     has staged the fault. Network loss can be simulated with the browser dev-tools "Offline" switch.
   - "Known Gaps" in the UCN files are NOT bugs - they are documented limitations. Do not log them.
   - Toasts (bottom-right) are how success and error messages appear. In add/edit/delete modals a
     validation error keeps the modal open and shows the message under its own input.

 UCN_SC_E028 - VIEW ACTIVITY LOG                       Actor: Admin         File: UCN_SC_E028_View_Activity_Log.md
==============================================================================================
 DO THIS ONE LAST. First generate some activity: sign in / out, one wrong password (e.g. commuter@gmail.com),
 suspend + reactivate a commuter (not pedro), change a vehicle status, edit two fare rates and save, add and
 delete a staff account, export a report CSV. Then read it all back as admin@gmail.com.

 MAIN FLOW
 [ ] 1. Click "Activity Log" in the sidebar (clipboard icon, after "Staff") -> entries newest first, 10 per page,
        with the total, the number written today and - when there are any - a "failed sign-ins in the last 24 h"
        link.
 [ ] 2. -> Each row shows When (Philippine time), Who (email + role, or "Not signed in / system"), What happened
        (category badge, event badge, readable description), Record (e.g. "Vehicle #12") and the IP address.
 [ ] 3. Click a row -> it expands: "What changed" (Field / Before / After table; fare-rate edits show a
        Distance / Regular / Discount table) plus extra facts (e.g. the suspension reason) and "Where it came
        from". Click again to close.
 [ ] 4. The entries you just caused are all present and correct: Signed in, Failed sign-in (no password in the
        entry), Signed out, Suspended / Reactivated (naming the admin), Updated vehicle (Status only in the
        diff), one Fare rates updated entry (saving again with no change adds none), Created / Deleted staff,
        Report exported.
 [ ] 5. Check things that must NOT create entries: browsing the map as guest / commuter, driver broadcasting
        and toggling availability, opening / filtering / paging the Activity Log itself, theme or font changes.

 ALTERNATE FLOWS
 [ ] A1. Search by an email, by a word from a description, and by the email a failed sign-in tried -> the right rows.
 [ ] A2. Pick a Category and/or an Event (e.g. Failed sign-in, Suspended, Fare rates updated) -> applied at once;
         combines with search and dates; survives paging.
 [ ] A3. Set from and/or to dates and Filter -> entries from the start of the first day to the end of the last day.
 [ ] A4. Press "Clear" -> the full list returns.
 [ ] A5. Press "Export CSV" -> smartcommute_activity_log_<YYYY-MM-DD>.csv (UTF-8; opens in Excel with the peso
         sign and arrows intact), honours the current filters, max 10,000 rows; the export itself adds an
         "Activity log exported" entry with the row count and filters.
 [ ] A6. Click the "failed sign-ins in the last 24 h" link -> filtered to Event = Failed sign-in from yesterday on.

 EXCEPTIONS
 [ ] E1. As driver manager, maintenance manager, driver or commuter open /activity-log (and the export) -> HTTP 403;
         as a guest -> redirected to login. The "Activity Log" menu item is only visible to admin.
 [ ] E2. "To" date earlier than "From" -> "The end date must be on or after the start date."; no result; the form
         is kept.
 [ ] E3. Edit the URL to an unknown category or event -> rejected with a validation message; no query runs.
 [ ] E4. Filters that match nothing -> "No entries match your filters" (or "Nothing has been recorded yet")
         instead of an empty table.
 [ ] E5. (*) More than 10,000 entries match the export -> only the newest 10,000 are exported. Mark [-] unless
         you have that much data.
 Also: light and dark mode read well; at phone width the filters stack and the table scrolls sideways.
